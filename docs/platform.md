# Platform layer (P1-01)

`internal/platform` is everything that is not a product module: configuration, the database pool and
migrations, the HTTP stack, idempotency, telemetry, the ops endpoints, and River. Product modules live
in `internal/<module>` and own exactly one PostgreSQL schema each.

## Processes

One image, three entrypoints. The Helm chart in relay-infra (`apps/relay-api`) runs each as its own workload.

| Binary | Runs as | Ports |
| --- | --- | --- |
| `/relay-api` | Deployment `relay-api` (HPA, PDB) | 8080 API (`/v0`, routed by the Gateway), 9090 ops |
| `/relay-worker` | Deployment `relay-worker` | 9090 ops |
| `/relay-migrate` | Argo CD Sync-hook Job, before both Deployments roll | none |

The ops port serves `/healthz` (liveness: the process answers, with no dependency checks), `/readyz`
(the database answers and has every migration this binary embeds; the worker also checks that River is running),
and `/metrics` (Prometheus). It is never exposed through the Gateway.

## Configuration

Environment variables, parsed into `config.Config` and validated at startup. Any error names the variable and
exits non-zero. `--print-config` prints the effective configuration with secrets redacted (a database
URL keeps its shape and loses its password). `--version` prints build metadata.

| Variable | Default | Meaning |
| --- | --- | --- |
| `RELAY_DATABASE_URL` | required, secret | `postgres://` URL |
| `RELAY_DB_MAX_CONNS` | `10` | Pool size per process |
| `RELAY_DB_CONNECT_TIMEOUT` | `5s` | |
| `RELAY_HTTP_ADDR` / `RELAY_OPS_ADDR` | `:8080` / `:9090` | |
| `RELAY_LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `RELAY_CORS_ALLOWED_ORIGINS` | empty (CORS off) | Comma-separated origins, such as the admin app. No wildcards |
| `RELAY_IDEMPOTENCY_TTL` | `24h` | Minimum `1h` |
| `RELAY_IDEMPOTENCY_LOCK_TIMEOUT` | `5s` | How long a duplicate waits for an in-flight request |
| `RELAY_MAX_REQUEST_BODY` | `1048576` | Bytes, on JSON operations |
| `RELAY_SHUTDOWN_TIMEOUT` | `20s` | Drain time after SIGTERM |
| `OTEL_TRACES_EXPORTER` | `otlp` | `otlp` or `none` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | SDK default | Plus every other standard `OTEL_*` variable |

## HTTP stack

```text
request ID → OTel span → observe (panic recovery, access log, metrics) → CORS → authenticate
  → router (relay-contracts gen/go, pinned in go.mod) → per operation: record route → authorize → idempotency → handler
```

- **Contract.** The router, types, and `StrictServerInterface` come from
  `github.com/gracefulinfra/relay-contracts/gen/go` at the tag in `go.mod` (P0-04 decision: the Go stub is a
  committed module in relay-contracts, so nothing is generated from the spec here). `api.Unimplemented`
  (generated by `make generate`) answers `501 not-implemented` for every operation, and modules override
  operations as they land. Changing the API means: change the spec in relay-contracts, tag it, and bump the module here.
- **Errors** are RFC 9457 `application/problem+json`, with `type` under `https://relay.dev/problems/`, a
  snake-case `code`, and the `requestId`. Unknown routes are `404 not-found`, and parameter errors are `400 bad-request`.
- **Auth hooks.** `auth.Authenticator` runs on every `/v0` request except `/v0/public/*`, which is
  anonymous. `auth.Authorizer` runs per operation, after routing, so it sees `r.Pattern` and the path values.
  P1-01 wires `auth.DenyAll` to both hooks, so every staff operation answers 401 until P1-02 plugs in Keycloak and RBAC.
- **Request IDs** come from a well-formed incoming `X-Request-Id` (Envoy sets one), or are generated. They are
  echoed in the response, and appear in access logs and problem documents.
- **Access logs** are one JSON line per request: method, path (never the query string), route pattern, status,
  bytes, duration, request ID, and trace ID. Headers and bodies are never logged.
- **Metrics** are `relay_http_requests_total{method,route,code}` and `relay_http_request_duration_seconds{method,route}`,
  labelled by route pattern, never by raw path. The OTel pool statistics (`pgxpool_*`) and River's OTel
  metrics are bridged into the same Prometheus registry.
- **Traces**: one server span per request, named after the route (`GET /v0/shows/{showId}`), with child
  spans for every SQL statement (otelpgx) and River job (otelriver).

## Idempotency

Every `POST`, `PUT`, `PATCH`, and `DELETE` requires exactly one `Idempotency-Key` (8–128 characters of
`A-Za-z0-9._:-`). The rules, and how each one is enforced:

| Rule | Mechanism |
| --- | --- |
| Scoped to actor, method, and resource | Primary key `(actor, method, path, key)` on `platform.idempotency_keys` |
| Binds the request body | SHA-256 of the body is stored. Reuse with a different body returns `409 idempotency-key-reused` |
| Authorization rechecked before replay | The authorize middleware runs before idempotency on every request |
| Effects and result persisted atomically | The key is claimed in a transaction, and the handler runs in it (`db.Querier`). The response is stored, then everything commits together |
| Concurrent requests serialized | A duplicate's claim blocks on the primary key until the first request ends, then it replays. After `RELAY_IDEMPOTENCY_LOCK_TIMEOUT` it gets `409 idempotency-key-in-progress` with `Retry-After` |
| Failures retryable | 5xx responses and panics roll the transaction back: no stored response and no side effects, so a retry with the same key runs again |
| Replay is faithful | Stored status, body, and `Content-Type`, `Location`, `ETag`, `Cache-Control`, plus `Idempotent-Replayed: true` |
| 24 h TTL without weakening uniqueness | Expired rows are ignored lazily, and deleted by the `platform.idempotency_cleanup` River job every 15 min. Business uniqueness lives on business tables and never depends on this table |

Module code must write through `db.Querier(ctx, pool)` and must never commit the request transaction.
Anything slow or external belongs in a River job enqueued in that transaction (P1-05), not in the request.
The tests are in `internal/platform/idempotency/idempotency_test.go`.

## Migrations

- `goose` SQL files in `db/migrations`, embedded in every binary. `relay-migrate up` applies them under a
  PostgreSQL advisory lock, with each migration in its own transaction.
- **Forward only.** There are no Down sections, and a bad migration is fixed by the next one.
- **Expand/contract.** During a rolling upgrade, the previous release runs against the new schema, so a
  release may only *add* (nullable or defaulted columns, new tables, new indexes created
  `CONCURRENTLY` in their own migration). Removing or renaming happens in a later release, once nothing
  reads the old shape. `/readyz` treats a database that is *ahead* of the binary as current, for this reason.
- One schema per module: `catalog`, `media`, `publishing`, `feeds`, `transcripts`, `community`,
  `analytics`, `billing`, `sponsorship`, `distribution`, plus `platform` (cross-cutting) and `river` (the job
  queue, whose SQL comes from the River CLI; see `00002_river.sql` for how to upgrade it).
- Queries live in `db/queries` and are compiled by sqlc (pinned image, `make generate`) into a package per module.
- Every migration is tested: the integration tests build every test database from the migrations, and
  `internal/platform/db` tests first install, re-run, a database ahead of the binary, and a failed upgrade.
  Tests against the seed data arrive with the seed data (P1-15).

## River

`relay-worker` runs a River client on the `river` schema, with two workers in the default queue (the laptop
profile). P1-01 registers only the idempotency cleanup job. P1-05 adds the job system proper.
